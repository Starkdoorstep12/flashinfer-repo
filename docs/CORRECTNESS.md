# Correctness Methodology

## How correctness is checked

Verified via `flashinfer-bench`'s local isolated runner against the
dataset's golden PyTorch reference implementation:

```bash
export FIB_DATASET_PATH=~/mlsys26-contest
flashinfer-bench run \
  --local ~/mlsys26-contest \
  --definitions dsa_sparse_attention_h16_ckv512_kpe64_topk2048_ps64 \
  --solutions TheRealDoers_V1 \
  --save-results --log-level DEBUG --timeout 60
```

This requires the solution to be registered in the local TraceSet
(`~/mlsys26-contest/solutions/dsa/dsa_sparse_attention_h16_ckv512_kpe64_topk2048_ps64/TheRealDoers_V1.json`,
generated by `python scripts/pack_solution.py` then copied there — this is
a local testing convenience, not something committed upstream to the
dataset repo).

## Tolerance and pass/fail logic

Default `flashinfer-bench` tolerances were used (no CLI overrides applied):
`atol = 1e-2`, `rtol = 1e-2`, `required_matched_ratio = 1.0`.

The evaluator (`flashinfer_bench/bench/utils.py::compute_error_stats`)
marks an output element as incorrect only if it fails **both** the
absolute and relative checks simultaneously:

```python
exceeds_tol_mask = (abs_error > atol) & (rel_error > rtol)
matched_ratio = 1.0 - (exceeds_count / total_elements)
exceeds_tol = matched_ratio < required_matched_ratio  # here: < 1.0
```

`required_matched_ratio = 1.0` means every single output element across
every workload had to satisfy `abs_error <= atol` **or** `rel_error <=
rtol`. This is the standard `torch.allclose`-style combined criterion,
which is designed to tolerate large *relative* error at near-zero reference
values as long as the *absolute* error stays small.

## Result

All 23 workloads in `dsa_sparse_attention_h16_ckv512_kpe64_topk2048_ps64`
passed:

- `max_absolute_error` consistently ≤ 0.015625 (== 2^-6, one bf16 ULP) —
  consistent with expected bf16 rounding, not a computational bug.
- `max_relative_error` ranged up to ~320x on some workloads. **This looks
  alarming out of context but is not a correctness problem**: it occurs
  exclusively at output elements where the golden reference value itself is
  very close to zero, so dividing a tiny (bf16-rounding-scale) absolute
  error by a tiny reference value inflates the relative-error metric. Since
  the pass/fail check is an AND (not OR) of the two tolerances, these
  elements still passed on the absolute-error term.
- Speedup vs. the golden reference ranged ~21x–34x across workloads. This
  reference is a naive per-token Python for-loop (see `indexer_kernel.py`'s
  `run()`) — a correctness baseline, not a performance baseline. **This
  number should not be reported as "faster than FlashInfer"** — see the
  caveat below.

## What this result does NOT show

The FlashInfer production baseline (`flashinfer_wrapper_5af199`, using
`flashinfer.decode.trtllm_batch_decode_with_kv_cache_mla`) could not be
benchmarked on this hardware — it fails with `ValueError: XQA MLA does not
support sparse_mla_top_k`. Its `target_hardware` is declared as
`["NVIDIA B200"]`; the XQA-based decode kernel path is architecture-specific
and appears unsupported on Ada-class GPUs (RTX 6000 Ada) in the installed
`flashinfer==0.6.16.post3`. Comparison against the real production baseline
is therefore not currently possible on this hardware and is left for future
work on B200 hardware, if available.

**For any reporting/paper use:** cite the speedup as "vs. naive per-token
reference implementation," not "vs. FlashInfer," and note the baseline's
hardware restriction explicitly.
